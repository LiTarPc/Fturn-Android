# Экспериментальный IP-туннель роутера

Ветка `codex/router-ip-tunnel`, база — тестовая миграция на sing-box 1.14.4. Этот режим не входит в стабильный релиз 4.3.8. Отдельный debug-пакет — `com.litar.freeturn.routerip`, имя — «Fturn IP-туннель TEST».

## Путь пакетов

OpenWrt принимает трафик LAN и передаёт целые IPv4-пакеты в UDP через USB-сеть (Linux FOU, ipproto 4). Новый вход `fturn-fou` в libbox принимает их в отдельный пользовательский стек gVisor. Соединения проходят через действующий route/DNS/outbound Fturn, включая RAW, VLESS или WireGuard. Ответные пакеты отправляются фиксированному peer через тот же UDP-сокет. Android VPN TUN не используется как очередь для внешних исходящих пакетов. RAW/TURN-ядра этим изменением не модифицируются.

Приёмник слушает заданный частный IPv4 и порт, проверяет внешний адрес и порт peer, разрешённую внутреннюю подсеть, IPv4/IHL/total length/TTL и контрольную сумму заголовка. Внутренние фрагменты передаются сетевому стеку. MTU по умолчанию 1350, диапазон 576–1400. Очереди ограничены сокетом и стеком; UDP NAT ограничен 4096 потоками. Счётчики входящих/исходящих пакетов, байтов, отклонённых пакетов и ошибок записи находятся в native-приёмнике.

FOU не содержит шифрования или аутентификации. Режим предназначен для выделенного USB-сегмента с одним фиксированным peer. Испытание по LAN допустимо только в контролируемой локальной сети с теми же ограничениями. IPv6 через этот вход не поддерживается.

## Настройки приложения

Добавлен автоматический режим с однократной привязкой по коду. Порядок подключения, файлы сервиса и ограничения описаны в [инструкции автопривязки](router-ip-auto.md). Ручной режим сохранён для совместимости; ниже приведены также результаты первоначального прототипа.

Карточка «IP-туннель роутера» находится рядом с настройками SOCKS5-раздачи на экране режима подключения. В обычном виде показаны переключатель и два адреса USB-сети. Подсеть LAN, UDP-порты обеих сторон и MTU скрыты в разделе «Дополнительно». В первоначальном прототипе MTU 1280 было консервативным стартовым значением. Текущий default — 1350 после USB-проверки; оно независимо от MTU удалённого VPN-профиля. По умолчанию вход выключен. Изменения применяются при следующем подключении VPN. В ручном режиме после изменения USB-подсети адреса нужно обновить; автоматический режим определяет их заново. После восстановления резервной копии вход выключается до проверки адресов.

Официальные `kmod-fou`, `kmod-ipip`, `kmod-iptunnel`, `kmod-iptunnel4`, `kmod-udptunnel4`, `kmod-udptunnel6` совпали с ABI. `ip-full` и недостающие библиотеки вместе с модулями распакованы временно в `/tmp/fturn-fou-probe-20261112`; SHA-256 пакетов проверены по официальному Packages.gz. Создание и удаление FOU-порта и IPIP/FOU-интерфейса проверено без добавления маршрутов. В постоянную флеш-память пакеты не установлены.

## Пример ручной настройки OpenWrt

Ниже шаблон, а не готовая команда переключения всей домашней сети. Подставить фактические USB-адреса. Сначала проверить отдельный тестовый маршрут и обратные ответы. Действующие правила блокировки выхода в обход VPN сохранять.

```sh
PHONE=10.42.0.1
ROUTER=10.42.0.2
PORT=40080
ip fou add port "$PORT" ipproto 4 local "$ROUTER"
ip link add ftfou type ipip remote "$PHONE" local "$ROUTER" ttl 64 \
  encap fou encap-sport "$PORT" encap-dport "$PORT"
ip link set ftfou mtu 1350 up
```

В Fturn соответствуют: listen=PHONE, peer=ROUTER, оба порта PORT, sourceCidr=подсеть LAN. Для возврата пакетов на Linux нужен FOU-порт приёма. Перед общим переключением проверить firewall, policy routing, DNS роутера, MSS/фрагментацию и отсутствие обхода при недоступном телефоне. Автоматическое переключение и восстановление выполняет отдельный помощник, описанный в инструкции автопривязки; этот ручной пример сам по себе его не запускает.

Откат тестового интерфейса:

```sh
ip link del ftfou
ip fou del port "$PORT" local "$ROUTER"
```

## Воспроизведение проверки

`build-libbox.ps1`/`.sh` применяют `patch-fou.py`. Исходники приёмника и тестов хранятся в `scripts/patches/fou`. `verify-libbox.py` отвергает старую AAR без нового входа. `test-libbox.ps1`/`.sh` повторяют native-тесты 20 раз.

Транспортные тесты проверяют реальный двусторонний TCP/UDP через UDP-инкапсуляцию, отказ постороннему peer, валидацию пакетов и завершение idle-обработчиков. Они прошли на Windows и Android; тест соединений на Android повторён 100 раз. Это локальная проверка транспорта, без VPN-сервера.

Для сквозной проверки подготовлен `scripts/tests/fou_client_probe.go`: две независимые внутренние IPv4, DNS через UDP/TCP и HTTPS с проверкой сертификата через вход телефона. Результаты приложения, USB-интеграции и сравнение производительности должны фиксироваться отдельно. Пока нельзя заявлять прирост скорости, проверку CS2, длительную устойчивость или работу автоматического восстановления USB.

## Результаты проверки приложения на Honor

- Отдельный APK установлен на Honor TFY-LX1, пакет `com.litar.freeturn.routerip`; основное приложение и его профили сохранены.
- Пройдены 215 JVM-тестов и Android lint. Последняя native-версия, включая одновременный запуск/остановку, проверена на Android в 100 повторах.
- Клиент на компьютере отправлял настоящие IPv4-пакеты в UDP на Wi-Fi-адрес телефона. Два независимых внутренних адреса проверили DNS UDP, DNS TCP и HTTPS с проверкой сертификата: VLESS 6/6, повторный RAW 6/6. Счётчики выбранного VPN-ядра увеличивались в обе стороны.
- В первоначальном RAW-прогоне было 5/6: один первый UDP DNS-запрос завершился тайм-аутом. В повторном прогоне он прошёл. Причина единичной потери не установлена; исправленной её не считаем. Исходный результат сохранён отдельно.
- Приёмник штатно остановлен после обоих протоколов. Затем в тестовой копии подготовлен собственный RAW-профиль телефона и SOCKS5 на 1080 с действующими параметрами роутера. На мобильной сети отдельно прошли авторизованные HTTPS и DNS TCP через SOCKS5.
- Wi-Fi возвращён в исходное выключенное состояние. Временная зашифрованная копия профилей, одноразовый ключ, приватные входные файлы, native-тестовый бинарник, instrumentation APK и ADB-forward удалены. Тестовое приложение оставлено установленным с работающим RAW и совместимой SOCKS5-раздачей.
- Тестовые FOU/IPIP-модули и инструменты выгружены/удалены из RAM роутера. HEV продолжает работать; свободное место `/overlay` осталось 1008 КиБ. Постоянная конфигурация роутера не менялась.

## Проверка физического USB-пути 12 ноября 2026

Honor TFY-LX1 с тестовым APK подключён к USB роутера. Фактические адреса: телефон `10.40.221.7`, роутер `10.40.221.226`, LAN `192.168.1.0/24`. На обеих сторонах установлен MTU 1350. Linux FOU/IPIP работает через `usb0` с MTU 1500; интерфейс `ftfou0` и policy table 40080 созданы временно в RAM.

На проверяющем компьютере работает собственный VPN. Его обычные успешные запросы не считаются доказательством FOU: первоначально счётчики туннеля оставались нулевыми. Для проверки использованы отдельные LAN-порты роутера с ограниченным DNAT только для IP тестового компьютера `192.168.1.238`. После DNAT пакеты направляются policy routing в FOU. Это пересылка ядром Linux без пользовательского TCP-прокси; глобальные настройки VPN компьютера не изменялись.

Через подтверждённый USB FOU-путь прошли DNS по UDP (61 байт, 0,198 с), DNS по TCP (61 байт, 0,032 с) и HTTPS с проверкой сертификата (928 байт, 0,406 с). Счётчики `ftfou0` увеличились на 14 исходящих и 18 входящих пакетов; firewall подтвердил оба направления.

Первая короткая загрузка 8 000 000 байт через FOU дала 26,33 Мбит/с на фазе чтения тела и среднюю загрузку CPU роутера около 42,7%. HEV сначала не работал: телефон отклонял подключения к TCP-порту 1080. Пользователь включил SOCKS5-раздачу и переподключил VPN; доступность порта и авторизация с текущими данными роутера затем подтверждены.

После этого выполнено сравнение на одном сервере `speed.cloudflare.com` (`162.159.140.220`): одна загрузка ровно 8 000 000 байт на каждый режим, сначала HEV, затем FOU, с одинаковым DNAT на роутере и проверкой TLS-сертификата.

| Показатель | HEV | FOU / MTU 1350 |
|---|---:|---:|
| Скорость чтения тела | 14,04 Мбит/с | 28,25 Мбит/с |
| Скорость с учётом подключения и TLS | 11,62 Мбит/с | 24,07 Мбит/с |
| Полное время запроса | 5,508 с | 2,659 с |
| Средняя загрузка CPU роутера | 61,2% | 55,1% |
| CPU процесса HEV | 51,7% | 0,0% |

Маршруты проверены перед каждой передачей. В HEV-прогоне `ftproxy0` принял 8 251 455 байт, `ftfou0` — 0. В FOU-прогоне `ftfou0` принял 8 368 172 байта, счётчики HEV не изменились. Разница подтверждает обход HEV новым путём. Скорость чтения тела в этой паре замеров выросла примерно вдвое. Это единичные последовательные запросы в мобильной сети; результат не доказывает максимальную скорость или длительную устойчивость. Средняя загрузка CPU относится к каждому полному запросу, длительность запросов различается.

После отката подтверждены отсутствие тестовых policy/forward/DNAT-правил, FOU-интерфейса и FOU-listener на роутере, работа HEV и успешный DNS-запрос самого роутера через HEV к `1.1.1.1`. Вся LAN оставлена на прежнем HEV-маршруте.

Тестовые правила ограничены выбранными адресами и одним компьютером. На каждый запуск предусмотрен автоматический откат через 360 секунд; после замера выполнен ручной откат. Постоянная конфигурация роутера и flash не изменялись. Загруженные модули и инструменты остаются временно в RAM.
